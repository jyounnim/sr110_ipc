# Lab 01: Hello IPC — 트러블슈팅 노트

이 문서는 Lab 01 개발/실기 검증 과정에서 실제로 겪었던 문제와 해결 과정을 기록합니다. 현재 최종 코드에는 이미 모든 수정이 반영되어 있으며, 이 문서는 참고용 기록입니다.

## 진단용 ack가 코드에 포함된 이유

Lab 01은 원래 M55 → M4 방향의 일방적인 신호 전송만을 목표로 설계되었습니다(양방향 통신은 Lab 03에서 정식으로 다룸). 그런데 개발/검증 당시 M4 쪽의 물리 콘솔(별도 UART)을 아직 연결하지 못한 상황이 있었고, 이 상태에서는 M55 콘솔만으로는 "M4가 ping을 제대로 받고 있는지", "LED0 토글이 실제로 성공했는지"를 전혀 알 수 없었습니다.

그래서 M55 콘솔 하나만으로 M4의 상태를 확인할 수 있도록, M4가 ping을 받을 때마다 그 처리 결과(성공/실패/디바이스 미준비)를 `struct ipc_ack_msg`에 담아 M55로 회신하는 임시 진단 경로를 추가했습니다. M55 콘솔에서 다음 로그로 상태를 구분할 수 있습니다.

- `[ACK] seq=N M4 alive, LED0 toggle OK` → M4가 정상적으로 ping을 받고 있고, LED0 GPIO 쓰기(I2C 트랜잭션)도 성공했다는 뜻입니다. 그런데도 실제 LED가 안 켜진다면 물리 배선(하드웨어) 쪽 문제일 가능성이 높습니다.
- `[ACK] seq=N M4 alive, but LED0 device NOT READY` → M4는 살아서 ping을 받고 있지만, `led0`(gpio_exp0) 디바이스 자체가 부팅 시 준비되지 않았습니다. I2C1/gpio_exp0 초기화 실패(예: PCA6416A가 실제로 응답하지 않음) 쪽을 봐야 합니다.
- `[ACK] seq=N M4 alive, LED0 toggle FAILED ret=N` → M4는 살아있고 디바이스도 준비는 됐는데, GPIO 쓰기(I2C 트랜잭션) 자체가 에러 코드 N으로 실패했습니다. I2C 버스 상태나 배선을 의심할 수 있습니다.
- **ack 로그가 아예 안 뜬다면** → M4가 부팅을 못 했거나, ping을 아예 못 받고 있거나(IPC 자체 문제), M4→M55 방향 mbox 채널에 문제가 있다는 뜻입니다. 가장 근본적인 문제이므로 우선적으로 확인해야 합니다.

참고로 이 진단 경로를 추가하기 전의 초기 코드는 `led0` 준비/설정에 실패하면 M4의 `main()`이 그 자리에서 바로 `return`해버리는 구조였습니다. 이 경우 mbox 콜백 등록 자체가 이뤄지지 않기 때문에, "IPC는 되는데 LED만 실패"인지 "M4가 그 지점까지도 못 갔는지"를 M55 쪽에서 전혀 구분할 수 없는 문제가 있었습니다. 이후 `led0` 실패해도 IPC/ack 경로는 계속 살아있도록 수정해서, 위 네 가지 케이스로 원인을 좁힐 수 있게 했습니다.

이 ack 경로는 원래 진단용 임시 코드로 추가된 것이지만, M4 콘솔을 직접 볼 수 있게 된 이후에도 회귀 테스트용으로 유용해 최종 코드에 그대로 남겨두었습니다. 동작 자체에는 영향이 없습니다.

## 해결된 이슈 1 — M4/M55가 물리적으로 같은 I2C1 버스를 공유

**증상**: M55 콘솔에는 `Ping sent, seq=N`이 정상적으로 매초 출력되지만, M4가 제어해야 할 LED0가 깜빡이지 않음. M55 단독 LED blink 샘플로는 LED0/LED1 모두 정상 동작.

**원인**: `sr100_rdk_sr100_m4.dts`와 `sr100_rdk_sr100_m55.dts`를 대조해보니, 두 코어의 `&i2c1`이 **완전히 동일한 물리 핀**(`i2c1_ms_scl_b`, `i2c1_ms_sda_b`)을 pinctrl로 참조하고 있었습니다. 즉 M4의 I2C1과 M55의 I2C1은 별개의 버스가 아니라 **같은 물리 I2C1 버스를 공유**하며, 여기에 LED0/LED1/버튼이 달린 `gpio_exp0`(PCA6416A, 0x20) 하나가 물려있는 구조입니다.

그런데 두 보드의 기본(base) dts 모두 애플리케이션 코드와 무관하게 `&i2c1 { status = "okay"; ... }`가 켜져 있어서, M4+M55를 함께 빌드하면 **두 코어가 부팅 시 동시에 같은 물리 I2C1 버스를 마스터로 초기화**하려고 시도합니다. 이 충돌 때문에 M4의 `gpio_pin_set_dt()` I2C 쓰기가 조용히 실패한 것으로 보입니다 (M55 단독 빌드에서는 이 충돌이 없으니 정상 동작).

**조치**: `lab/boards/sr100_rdk_sr100_m55.overlay`에 `&i2c1 { status = "disabled"; };`를 추가해, LED/버튼을 실제로 구동하는 M4만 이 버스를 갖도록 수정했습니다. 이 수정은 Lab 01~18 전체의 M55 오버레이에 동일하게 반영되어 있습니다 (다른 랩들도 i2c1을 만지지 않으므로 안전).

> 참고: 이 조치로 M55 쪽에서는 `vcc_sd1` 레귤레이터(SD카드용, `gpio_exp0 7`)와 카메라(`ov02c10`) 전원 제어(`gpio_exp0 8/13`)도 함께 비활성화됩니다. 이 IPC 랩들에서는 SD카드/카메라를 쓰지 않으므로 문제없지만, 이 오버레이를 다른 용도로 재사용할 땐 참고해야 합니다.

## 해결된 이슈 2 — `&i2c1` disable만으로는 부족 (M55 빌드 에러)

이슈 1의 조치(`&i2c1 { status = "disabled"; };`)만 넣고 M55를 빌드하면 아래처럼 실패합니다.

```
FAILED: .../gpio_pcal64xxa.c.obj
.../zephyr/include/zephyr/device.h:96:41: error: '__device_dts_ord_23' undeclared here
```

**원인**: devicetree에서 부모 노드(`&i2c1`)를 disable해도, **자식 노드(`gpio_exp0`)는 자기 `status`가 명시돼 있지 않으면 기본값 `"okay"`를 그대로 유지**합니다. 그래서 `nxp,pcal6416a` GPIO expander 드라이버(`gpio_pcal64xxa.c`)는 여전히 "활성 인스턴스"로 인식돼 컴파일 대상에 포함되는데, 그 안에서 `DT_BUS(node_id)`로 부모 I2C1 버스의 디바이스 핸들을 참조하려다 — 그 버스가 disable돼서 핸들 자체가 생성되지 않았으니 — 컴파일 에러가 납니다.

**조치**: M55 오버레이에 자식 노드도 명시적으로 disable을 추가했습니다.

```dts
&gpio_exp0 {
    status = "disabled";
};

&ov02c10 {
    status = "disabled";
};
```

(`ov02c10`는 M55 base dts에 있는 카메라 센서 노드로, 같은 이유로 함께 꺼둡니다.) Lab 01~18 전체 M55 오버레이에 반영 완료했습니다.

## 해결된 이슈 3 — `M4_BUILD` 상대경로 기준

**증상**: M55는 정상 동작하지만 M4는 부팅조차 안 되는 것처럼 보임.

**원인**: `west build` 명령에서 M55 빌드에 M4 이미지를 포함시키기 위해 지정하는 `-DM4_BUILD=...` 값이, 명령을 실행하는 현재 작업 디렉토리(CWD)가 아니라 **M55 빌드 디렉토리(`-d`로 지정한 디렉토리, 예: `m55/`) 기준 상대경로**로 해석됩니다. 이는 `zephyr_srsdk/soc/syna/astra_sr/sr100/CMakeLists.txt`의 다음 로직 때문입니다.

```
find_file(M4_ELF ... PATHS ${CMAKE_BINARY_DIR}/${M4_BUILD}/zephyr/ NO_DEFAULT_PATH)
```

`m4/`와 `m55/`가 서로 형제 디렉토리인 구조에서는 `./m4`가 아니라 **`../m4`**가 맞는 값입니다. `./m4`로 지정하면 `NO_DEFAULT_PATH` 옵션 때문에 CMake가 에러 메시지 없이 조용히 `M4_ELF`를 찾지 못하고, 이후 `srsdk_image_generator.py`가 `-m4_image` 인자 없이 호출되어 **최종 flash 이미지에 M4 펌웨어가 아예 포함되지 않는** 결과로 이어집니다. 겉으로는 M55는 정상 동작하고 M4만 부팅이 안 되는 것처럼 보여서 원인을 특정하기 어려운 유형의 문제였습니다.

**조치**: `west build` 명령의 M55 빌드 인자를 `-DM4_BUILD="../m4"`로 고정했습니다. 이 값은 M4/M55 빌드 디렉토리를 형제 디렉토리로 두고 빌드하는 이 커리큘럼의 표준 빌드 순서(`-d m4`, `-d m55`)를 그대로 따르는 한 항상 유효합니다.

## Lab 01 최종 검증 완료

`M4_BUILD="../m4"` 수정 후 재빌드/재플래시로 M55/M4 콘솔 양쪽 정상 출력 및 실제 LED0 토글까지 확인 완료했습니다.

- M55: `Ping sent, seq=N` + `[ACK] seq=N M4 alive, LED0 toggle OK` 매초 정상 출력
- M4: `[Toggle_Task] ping seq=N -> LED0 toggle ret=0` 매초 정상 출력, LED0 실제 깜빡임 확인

## 개발 중 확인이 필요했던 사항 (모두 확인 완료)

코드 작성 시점에는 실제 west/HAL 빌드 환경 없이 devicetree/샘플 패턴 분석만으로 작성된 부분이 있어, 다음 항목들을 실기 빌드/테스트로 별도 확인했습니다. 현재는 모두 확인이 끝난 상태입니다.

1. **`CONFIG_GPIO_PCA95XX` 심볼**: 실제 빌드 로그에서 `gpio_pcal64xxa.c`가 이 Kconfig 심볼과 무관하게 자동으로 컴파일 대상에 포함되는 것을 확인했습니다 — devicetree에 `nxp,pcal6416a` 노드가 `okay` 상태로 있으면 Kconfig가 이를 보고 자동 선택(`default y if DT_HAS_...`)하는 방식으로 동작하는 것으로 보입니다. `CONFIG_GPIO_PCA95XX` 자체는 존재하지 않는 심볼일 가능성이 높지만(무시되는 것으로 추정), M4 쪽 LED 동작 자체는 실기로 정상 확인되었습니다.
2. **M55 기본 콘솔 UART**: M55 기본 콘솔은 `ns16550_uart1`, 230400bps로 base dts에 이미 설정돼 있어 오버레이가 별도로 필요하지 않음을 확인했습니다.
3. **`DT_PATH(mbox_consumer)`**: M55 쪽 base dts에도 `mbox-consumer` 노드가 기본으로 존재함을 확인했습니다 (`mboxes = <&ipc0 1>, <&ipc0 0>;` — tx/rx 순서가 M4와 반대로 매핑되어 있는 것이 정상입니다).
