# Lab 10 트러블슈팅: 임계값 이벤트 알림

Lab 10을 실기(sr100_rdk 보드)에서 검증하는 과정에서 실제로 겪었던 문제와 조치를 정리합니다. 노드 레이블(`mc3479`), status 재활성화, ODR wake, `SENSOR_ATTR_FULL_SCALE`/sensitivity 관련 이슈는 Lab 09에서 이미 확인·반영된 사항이라 이 문서에는 포함하지 않습니다 (해당 내용은 [Lab 09 트러블슈팅](../../09_accel_telemetry/doc/09_accel_telemetry_troubleshooting_kr.md) 참고).

---

## 이슈 1 — 정지 상태에서도 이벤트가 계속 발생

### 증상

M55 콘솔에서 보드를 가만히 두었는데도 부팅 직후부터 `THRESHOLD EVENT`가 끊임없이 발생했습니다.

```
[00:00:10.624,000] <wrn> lab10_host: THRESHOLD EVENT seq=21 x=358 y=-236 z=-10186
[00:00:11.128,000] <wrn> lab10_host: THRESHOLD EVENT seq=22 x=193 y=0 z=-10092
...
```

### 원인

로그의 z축 값이 항상 -10000대에 머물러 있는 것에서 알 수 있듯, 정지 상태에서도 중력가속도(~1g)가 raw 값에 항상 실려 있었습니다. 당시 코드는 원점(0,0,0)을 기준으로 magnitude(원시값의 절대 세기)를 임계값과 비교하고 있었기 때문에, 보드가 어떤 자세로 놓여 있든 중력 성분만으로 이미 임계값을 넘어버려 가만히 있어도 항상 "초과"로 판정됐습니다. 즉 "얼마나 움직였는가"가 아니라 "중력을 포함한 절대 세기가 얼마나 큰가"를 재고 있었던 것이 문제였습니다.

### 조치

사용자에게 "이 캘리브레이션은 M4에서 하는 게 맞겠지?"라고 확인받은 뒤, 센서를 물리적으로 구동하는 쪽이 M4이므로 **M4에서** 캘리브레이션을 수행하도록 설계했습니다:

- 부팅 직후 약 1초(`CALIB_SAMPLES` = 10회 × `POLL_PERIOD_MS` = 100ms) 동안 샘플을 모아 X/Y/Z 평균을 baseline으로 저장.
- 이후 모든 샘플은 이 baseline과의 편차(`dx = x - base_x`, `dy = y - base_y`, `dz = z - base_z`)를 임계값과 비교하도록 변경.

이렇게 하면 중력 오프셋과 부팅 시점의 고정 기울기가 baseline에 흡수되어 상쇄되고, 실제 "움직임"만 이벤트로 잡히게 됩니다.

**주의**: 이 baseline은 부팅 시 한 번 찍는 고정 스냅샷이며, 계속 갱신되는 적응형(adaptive) 필터가 아닙니다. 캘리브레이션 중(부팅 후 약 1초)에 보드를 움직이면 그 움직임이 그대로 baseline에 섞여 들어가 이후 판단이 왜곡됩니다.

## 이슈 2 — 캘리브레이션 후에도 여전히 노이즈로 임계값을 넘음, 임계값 상향

### 증상

이슈 1의 캘리브레이션을 적용한 뒤에도, 보드를 가만히 두면 여전히 이벤트가 계속 발생했습니다. M4 콘솔 로그:

```
[00:00:12.017,000] <inf> lab10_client: [Threshold_Task] event sent seq=8 mag=1201 (dev x=73 y=35 z=-1093)
[00:00:12.723,000] <inf> lab10_client: [Threshold_Task] event sent seq=9 mag=1515 (dev x=-328 y=-29 z=-1158)
```

`dev z`(baseline 대비 z축 편차)가 정지 상태에서도 계속 -1000 ~ -1190대에 머물러 있었고, 여기에 x/y의 작은 노이즈가 더해지면서 `mag`이 당시 임계값 1200을 반복적으로 넘겼습니다.

### 원인

캘리브레이션으로 부팅 시점의 고정 오프셋(중력 성분 + 초기 기울기)은 상쇄됐지만, 이 보드/센서 개체에서 남는 **잔차 노이즈**(baseline 자체가 흔들리는 폭)가 실측으로 최대 `mag≈1515`까지 나타났습니다. 원래 설정했던 임계값 1200은 이 잔차 노이즈의 최댓값보다도 작은 값이었기 때문에, 정지 상태에서도 항상 넘길 수밖에 없었습니다.

### 조치

사용자 요청에 따라 임계값을 **2000 milli-g**로 상향했습니다:

- M55: `lab/src/main.c`의 `ACCEL_THRESHOLD_MILLI_G`
- M4: `lab/remote/src/main.c`의 `threshold_milli_g` 기본값

(두 값 모두 M55가 부팅 시 `IPC10_CMD_SET_THRESHOLD` 커맨드로 M4에 재설정하므로, 실제로는 M55 측 값이 최종적으로 적용됩니다. 다만 M4 쪽 기본값도 일관성을 위해 함께 맞췄습니다.)

2000은 실측된 노이즈 최대치(mag≈1515)보다 충분히 여유 있는 값입니다. 다만 이 값은 하드웨어 개체차나 설치 환경(보드 고정 방식, 진동원 근접 여부 등)에 따라 다시 튜닝이 필요할 수 있습니다. 정지 상태에서 M4 콘솔에 찍히는 `mag` 값을 몇 번 관찰해서, 그 최댓값보다 확실히 큰 값으로 임계값을 잡는 것을 권장합니다.

## 설계 노트 — mbox 콜백은 절대 블로킹 금지

Lab 03/Lab 07에서 확립된 원칙대로, M55/M4 양쪽 `rx_cb()` 모두 무거운 처리를 하지 않고 즉시 반환합니다 — M4는 커맨드를 큐에 넣기만 하고(`k_msgq_put(..., K_NO_WAIT)`), M55는 이벤트 내용을 로그로 남기기만 합니다. M4의 실제 처리(가속도계 폴링/캘리브레이션, 임계값 갱신, `mbox_send_dt()` 호출을 포함한 이벤트 전송)는 전부 `Threshold_Task` 워커 스레드에서 수행되므로, 이 랩은 처음부터 이 원칙을 위반한 적이 없습니다.
