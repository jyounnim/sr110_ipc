# Lab 03: Full-Duplex Ping-Pong — 트러블슈팅

이 문서는 Lab 03을 실제 하드웨어에서 검증하는 과정에서 겪은 구체적인 증상과 원인, 조치 이력을 정리한 것입니다. 개념 설명(왜 mbox 콜백이 블로킹되면 안 되는지 등)은 [`03_full_duplex_ping_pong_kr.md`](./03_full_duplex_ping_pong_kr.md)를 참고하세요. 여기서는 실제로 발생했던 이슈와 그 재현/해결 과정만 다룹니다.

## 증상 / 원인 / 조치

### 증상: M55 콘솔에 아무 로그도 출력되지 않음 (부팅 배너조차 없음)

M4는 ping을 받아 LED0 토글 + pong 응답까지 정상 수행하고 다음 ping을 계속 기다리는데, M55 콘솔에는 부팅 배너조차 뜨지 않았습니다(로그가 아예 하나도 없음). M55는 최초 ping은 보냈지만(M4가 seq=1을 정상 수신했으므로 확인됨) 그 이후로는 완전히 응답이 없는 상태로 멈췄습니다.

**원인**: M55의 `mbox_rx_callback()`(pong 수신 콜백) 안에서 `k_msleep(PINGPONG_DELAY_MS)`를 직접 호출하고 있었습니다. mbox 수신 콜백은 ISR(인터럽트) 컨텍스트에서 실행되는데, `k_msleep()`처럼 스레드를 재우는 블로킹 호출은 ISR 안에서 쓰면 안 됩니다 — 커널이 그 자리에서 멈춥니다(hang).

Zephyr의 로그 기본 모드(지연 처리)는 로그를 버퍼에 쌓아뒀다가 별도 로깅 스레드가 나중에 출력하는 방식인데, ISR에서 커널이 멈춰버리면 그 로깅 스레드가 스케줄될 기회 자체가 사라져서, 부팅 배너를 포함해 이미 쌓여있던 로그까지 전부 화면에 못 뜨고 사라졌습니다. 이것이 겉보기엔 "M55가 아예 아무것도 안 한 것"처럼 보였던 이유입니다.

M4 쪽은 처음부터 콜백에서 큐에만 넣고 실제 처리(LED 토글 + pong 전송)는 워커 스레드에서 하는 정상 패턴을 썼기 때문에 문제없이 계속 동작했습니다. 이 대비(M4는 정상, M55만 멈춤)가 원인을 좁히는 데 핵심 단서가 되었습니다.

**조치**: M55도 M4와 동일한 ISR → `k_msgq` → 워커 스레드 패턴으로 재작성했습니다. `mbox_rx_callback()`은 이제 pong을 큐에 넣기만 하고, `k_msleep()` + 다음 ping 전송은 새로 추가한 `Pong_Task` 워커 스레드에서 처리합니다.

**재검증 결과 (2026-08-31)**: 수정본 재검증 결과 M55 부팅 배너가 정상 출력되고, PING/PONG seq가 계속 증가하며, M4 LED0도 주기적으로 정상 토글되는 것을 확인했습니다. 이 이슈는 완전히 해결되었습니다.

## 참고: gpio-keys 버튼을 쓰는 랩이라면 (이 랩은 해당 없음)

이 랩은 버튼을 쓰지 않아 아래 이슈가 해당되지 않지만, 버튼(`user_button`)을 사용하는 이후 랩(05, 15, 17, 18 등)에서는 Lab 02에서 확인된 이슈가 재발할 수 있습니다: 이 보드의 M4 쪽 `gpio_exp0`(PCAL6416A)는 `int-gpios`가 배선돼 있지 않아 인터럽트 기반 `gpio-keys`가 항상 `-ENOTSUP`(-134)로 실패합니다. M4 오버레이에 다음을 추가해야 합니다 (반드시 **부모** `gpio-keys` 노드에 붙일 것 — 자식 `user_button` 노드에 붙이면 devicetree 바인딩 에러가 발생합니다).

```dts
&buttons {
	polling-mode;
};
```

자세한 원인은 [Lab 02 트러블슈팅 문서](../../02_button_pong/doc/02_button_pong_troubleshooting_kr.md)를 참고하세요.
